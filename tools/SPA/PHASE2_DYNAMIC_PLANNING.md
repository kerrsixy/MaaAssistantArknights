# 卫戍协议·规程序列 I：第二阶段动态规划设计

第二阶段建立在第一阶段的完整流程状态机之上。第一阶段负责从开局、准备、战斗、悬赏/装备页一直走到结算；第二阶段只替换“每个准备窗口如何决策”的策略插件，不重写页面恢复、回合推进、战斗等待和结算记录。

## 1. 决策输入

每次准备窗口先生成不可变快照，再由各规划器读取：

- **局面**：规程难度、地图、当前回合、生命、敌人特性、Boss/非 Boss、剩余时间、剩余部署数。
- **禁用信息**：核心盟约、附加盟约、干员禁用列表；白色/灰白图标视为禁用，绿色图标视为可用。所有候选策略、盟约和干员先过禁用过滤器。
- **商店**：商店等级（卡面罗马数字对应可刷到的干员/装备等级）、升级价格、刷新价格、免费刷新次数、冻结状态、每个卡槽价格和识别置信度。
- **阵容**：备战区和装备区占用、同名复制数、精英化状态、已激活阵营、主/副盟约层数、可部署数、已上场位置和朝向。
- **库与特质**：当前版本策略、盟约、干员、装备、合成门槛、叠层特质、装备转职/阵营转换规则。普通三张合成不能覆盖特质明确的两张或其他特殊门槛。
- **目标**：未完成徽章优先级、已选策略、当前主副盟约、主叠层手、主输出手、Boss 预案。

开局策略选择使用 `opening_strategy_selection=true` 时，策略候选只把禁用盟约/策略和初始敌方条件作为硬过滤；主盟约尚未激活时，候选会标记为“临时选择”，进入商店发育后必须重新验证阵营激活、叠层手和输出手，不能把开局策略当成阵营锁定。

任何字段未知时，规划器必须返回“等待/补识别”，不能把未知当作 0、可买或已激活。

## 2. 策略、主盟约和副盟约选择

开局策略是偏好，不是锁定。先过滤禁用策略，再按未完成徽章、当前可用核心盟约、策略要求和地图/Boss 适配度评分。实际主盟约由卡池密度决定：

1. 统计当前商店、备战区和已上场干员的阵营密度；
2. 检查三人激活（或特质明确的两人激活）是否在可见商店等级和剩余回合内可达；
3. 检查该阵营是否同时存在可验证的主叠层手和终端输出手；
4. 只有达到激活条件且层数来源已出现，才锁定主线；否则保留转线候选。

副盟约按“与主盟约共享干员/装备、能补经济或生存、能提高层数上限”排序。远见、奇迹、投资人按本期明确规则计入整备区成员；调和需要在场成员或明确的特殊效果，不能默认备战区的调和也生效。调和给核心盟约增加一名激活人数，两个不同核心成员加调和可以激活三人核心；不把它解释成激活门槛增加，也不替代六名不同成员的额外效果要求。阵营激活、叠层手和输出手不要求在第一回合同时出现。

## 3. 商店与经济规划

每回合资金、刷新价和升级价都从当前界面读取；普通资金是否清零由当前策略/装备事实决定。规划器在时间预算内按以下顺序比较：

1. 维持能通过本回合战斗的最低阵容；
2. 买入已激活盟约所需的核心/叠层手；
3. 形成对子并在合成后获取高一级候选；
4. 购买一费卡作为已验证的买卖银行；
5. 升商店以打开叠层手（通常 III–IV）或输出手（通常 V–VI）的等级窗口；
6. 使用免费刷新，再决定付费刷新、冻结或结束准备。

升级器使用“当前等级”和“升级价格”两个独立字段，不能把卡面罗马数字或升级价格混为一谈。冻结只在下一回合自动刷新会损失已识别的关键卡时使用；已无关键卡、时间不足或资金不足时直接结束准备。备战区/武器区满时先清理或换装，不能继续购买。

每个准备窗口按“商店操作 → 备战整理 → 部署整理 → 战斗确认”循环，而不是只执行一次商店动作：先保证商店展开，完成升级、买卖、刷新和冻结；再判断备战区与场上部署区是否已满。若两边都满，先按出售评分清理需要卖出的单位；出售场上单位会释放部署位，出售备战单位会释放备战位，释放后重新进入下一轮商店与整理循环。若备战区未满，继续正常经济操作；若备战区有单位且部署位未满，优先把应上场单位整理到可见位置并部署。每轮都要重新读取资金、备战占用、剩余部署数和卡牌位置，不能用上一轮缓存代替。

## 4. 叠层与输出规划

每个盟约维护角色表：`activation_members`、`stackers`、`support_stackers`、`terminal_carries`、`transition_units`、`bench_only`。规划器以干员当前特质为准，分别计算：

- 该干员在备战区、部署时、战斗中、被击倒/复活、技能开启、击杀敌人、买卖人口、获得/更换装备时的层数贡献；
- 每回合层数上限与全局层数上限；
- 主叠层手和输出手所在商店等级，距离该等级还需要多少次升级；
- 需要主动触发的循环，例如不屈反复下场、森蚺击杀砾、白铁召唤物、归溟幽灵鲨傀儡锁血、炎国买卖人口、调和转职/阵营装备。

部署规划同时给出“本回合上场”和“本回合留在备战区”的清单。远见等明确写明“备战区生效”的干员不能为了凑人数强行上场；需要被击倒、复活或频繁再部署的干员必须保留部署额度和战斗时序。

## 5. 站位、技能和 Boss 重排

普通波次先使用已验证地图格、攻击范围、阻挡/治疗覆盖和敌人路径生成候选布局，再按以下目标排序：生存 > 覆盖主输出射程 > 触发叠层事件 > 复活/再部署循环 > 溢出输出。每次拖动都必须重新确认干员身份、格子、部署数和朝向。拖拽过程中地图会进入绿色可放置覆盖层，不能把普通地图点击当成放置输入；执行器只发送按住、移动、松开，并在松开后读取放置页/方向页。

地图地形是“可放置性”和“效果”的两套字段。以沼泽为例，沼泽格可以正常部署干员；它只会逐渐降低场上干员攻击速度，并逐渐降低经过敌人的攻击速度和移动速度。规划器应记录 `deployable=true`，再对干员和敌人分别施加地形效果评分，不能把沼泽当成禁用格或直接排除候选位置。执行部署时，先按住干员拖到屏幕左侧，让干员介绍淡化并重新获得完整地图；商店若处于折叠状态，可能覆盖最右侧备战干员，因此源干员扫描前应展开商店，不能默认折叠。若确认最右侧干员本回合不需要上场，可以先在展开商店状态下与一个同样不需上场的干员交换备战位置，再折叠商店；这只是可选的界面整理动作，不能用来替代身份核验。

将备战区干员拖到已有干员所在格时，游戏执行的是**替换**：新干员上场，原干员回到备战区，部署额度不按新增人口重复扣除。阶段二把它建模为 `replace_deployed_unit` 动作，前置条件是目标格原身份已核验、备战区有新干员、替换后两边身份和部署额度都能复核；任何一项未知都不能把替换当成普通部署。若商店折叠会盖住最右侧备战干员，先在商店展开状态下判断其是否需要上场；需要上场时把它与一个确认不需上场的备战干员交换位置，再折叠商店。折叠后按住要部署的卡拖到屏幕左侧，等待干员介绍淡化并识别完整地图，再移动到规划格并松手；若目标本来就在最右侧且无法安全交换，则保持商店展开，使用同一套左侧按住重识别流程。

已上场干员拖到另一个已上场干员的格子时，游戏执行的是**位置交换**；规划器必须记录两个格子的原身份和朝向，交换后分别复核。场上人数未满时，备战区的已购干员按“可提升当前战力/可触发层数/有合法绿色格”优先补上；场上人数已满时，只有替换收益明确且替换证据完整才换人。识别失败、资源矛盾或战力不足时保留当前阵容，不通过主动卖血换取操作空间。

干员战斗技能由游戏按模式规则自动释放，规划需要正确的技能预设、技力回复、站位和目标条件，不能虚构手动开干员技能的控制能力。策略的主动能力另行识别和执行，必须核验目标、次数、费用和结果；当前只覆盖部分能力，未完成全部策略的执行接线。

Boss 回合单独生成布局：重新识别 Boss 特性、冻结/致命/隐匿/飞行等标签，撤回不适配单位，重新安排主输出、治疗、阻挡和叠层触发位，再启动战斗。Boss 超时采用持续扣血模型，不能沿用普通波次“剩余敌人扣血上限”的结算假设。

敌人详情面板也属于第二阶段。战斗中点击右上角黄色敌人入口可打开详情，再次点击任意空白处恢复战斗视图；详情面板可以上下滑动，敌人条目会标明来源路（上两行从上路、下两行从下路）。第二阶段再把敌人类型、特性、来路和 Boss 机制接入站位与技能规划；第一阶段只等待战斗结束，不依赖敌人详情识别。

## 6. 悬赏、装备和异常

悬赏按“可完成性、收益、对当前阵容的风险”评分；无法识别敌人或确认按钮时停在可恢复检查点。装备规划按商店等级和已验证配方/转职规则选择，优先满足主输出、叠层循环和生存；装备替换会丢弃旧装备且不返还，必须在决策日志中写出被替换装备。装备区满、登录失效、跳出卫戍页面、黑屏或 OCR 矛盾都走重新观察/重连，不重开未结算对局。

## 7. 模块边界

当前代码入口使用 `dynamic_decision_mode=true`：它保留阶段一已经验证的拖拽、页面恢复和部署执行器，只替换准备窗口的最低价优先分支，启用阵营密度、叠层手/输出手和经济评分。`basic_mode` 仍保持开启是执行安全模式，不代表阶段二继续使用固定最低价决策。

命令行实机入口可使用 `phase1_runner.py --dynamic`。它仍然沿用阶段一的安全执行器和完整回合闭环，但准备窗口会启用动态阵营评分；当当前阵营没有可买的已识别卡、且升级价格和目标卡池等级均已验证时，每回合最多升一次商店，避免重复支付或把未知价格当作升级依据。未带 `--dynamic` 仍是阶段一最低价/固定升级日程。

保留第一阶段的 `StrongholdProtocol`、`RoundTaskPlugin`、结果审计和恢复状态机；第二阶段新增纯决策接口：

```text
SPADynamicSnapshot -> SPAStrategyPlanner
SPADynamicSnapshot -> SPAPactPlanner
SPADynamicSnapshot -> SPAEconomyPlanner
SPADynamicSnapshot -> SPAFormationPlanner
SPADynamicSnapshot -> SPABattleSkillPlanner
SPADynamicSnapshot -> SPARewardPlanner
```

每个规划器只返回带证据的动作计划（目标、前置条件、验证条件、失败恢复），执行器仍使用第一阶段的 guarded action。决策日志必须记录：策略、主/副盟约、主叠层手、主输出手、购买/升级/刷新/冻结理由、上场/下场/站位、技能、悬赏、战斗结果和回合号。

阶段二的验收顺序：先在固定低难度跑完整局；再验证动态转线；再验证商店升级和经济；再验证普通 Boss 重排；最后才加入特殊刷层循环与高难度通关。任何“无法识别、无法确认、资源状态矛盾”都应恢复或安全停在检查点，不能伪造胜利。
